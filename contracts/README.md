## Правила формата

- JSON: `snake_case`; C#: PascalCase; TypeScript: те же snake_case, что на проводе. Сериализация `JsonNamingPolicy.SnakeCaseLower`, строковые enum через `JsonStringEnumConverter(JsonNamingPolicy.SnakeCaseLower, allowIntegerValues: false)`. Числовые enum не принимаем.
- Время: ISO 8601 с часовым поясом; сервер хранит UTC, границы недели и бюджета считает по Europe/Moscow. DateOnly — `YYYY-MM-DD`. Все ID непрозрачные строки в API; в БД UUID, кроме company/group/source ID из входных данных/конфига.
- Число 0 означает нулевой известный показатель; `null` — неизвестно. JSON-массивы и словари обязательны, пустое значение — `[]` / `{}`. Nullable-поля передаём как `null`; только `forecast` опускаем целиком, если функция выключена.
- SQL numeric и C# decimal — для платежей и рублей LLM. В браузер не передаём сырые суммы платежей, граф контрагентов и чужие ID. API score/доли находятся в [0,1]; frontend их не пересчитывает.
- API принимает только входные DTO. role и company_id проверяет сервер, origin/review/critic/budget из пользовательского текста не принимаются. Закрытые внутренние поля не сериализуются через ORM-сущность напрямую.
- JSON Schema Draft 2020-12 уже подготовлены в schemas/ с запретом лишних полей. Адаптацию к поддерживаемому подмножеству шлюза проверяем в A01/A06. Между поставщиком LLM и API есть кодовые проверки: ответ модели не становится готовой карточкой напрямую.

Пересборка зеркал: `python contracts/generate.py`. Генератор поддерживает только используемый здесь простой синтаксис records/enum; после расширения C#-синтаксиса его нужно обновить, а не считать полноценным компилятором. Желаемые operator/manual DTO находятся в конце Api.cs, endpoints отделены в http.md.

## Минимальная карта классов

`company/company_profile → CompanyProfile`; `group_profile → GroupProfile`; результат score → `RankingResult`; JSON карточки → `InsightDto`; короткая строка → `FeedItemDto`; `background_job.payload → *Job`; `research_chunk.chart_data → ChartDraft + серверный review_status`; `llm_usage → LlmUsageEntry`.

ORM-классы создаём только в A02 из database.sql: одно имя таблицы — одна конфигурация EF Core; DTO и immutable records не обязаны быть EF entities. Отдельные классы для claim/evidence таблиц не нужны: они JSONB.

## Проверяемые инварианты

Claim ID уникален внутри карточки; каждый claim_id и ref разрешается. Один источник evidence может поддерживать несколько утверждений. Короткая строка имеет собственный evidence-реестр и reasons; claim_ids у её reasons пусты, поскольку полного инсайта ещё нет. В полной карточке reasons могут ссылаться на claims и evidence. confidence — необязательная оценка уверенности утверждения, не шкала влияния на бизнес.

`bank_view=not_found` → пустые claim_ids. `bank_analytics` требует банковский источник, дату и страницу; факт из PDF может иметь origin=source_fact. Evidence из OCR несёт статус сверки. Числа графиков при review_status≠reviewed не передаются агенту как численные входы. Исторический обзор не считается актуальной позицией банка автоматически.

`ready` означает готовую валидную карточку. `critic_passed` ставится только проверенным критиком утверждениям; починка без повторного критика не получает этот статус автоматически. Критик: 0/1 HTTP-запрос; общая починка: 0/1. Структурная ошибка после починки → failed, не публикация. Не подтверждённые по смыслу claims — только в ограничениях, не в actions/headline или основании score.

Ни один контракт не содержит event_type, direction/novelty/horizon события, шкалу влияния, предложения банка, SSE или настройки модели из браузера. Направление платежа incoming/outgoing и sign матрицы — отдельные реальные признаки, они остаются.

Forecast при выключенном серверном флаге удаляется кодом, даже если модель самовольно вернула его. Estimated требует low/high, unit=`%` либо `pp`, входы/формулу/допущения; insufficient_data требует missing_data и low/high=null. Эта функция желательная, а не условие готовности каждой карточки.
