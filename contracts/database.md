# База данных

[database.sql](database.sql) — полный перечень полей и типов, а не SQL, уже выполненный в приложении. Применяет Артём через миграцию A02. Не создаём вторую схему в персональных задачах.

## Состав

| Таблица | Для чего / класс |
| --- | --- |
| company | Доступный CLIENT; исходные 24 поля в raw_data, часто используемые поля вынесены в колонки |
| payment | Ребро PAYER → BENEFICIARY, сумма и число платежей; без самопереводов |
| company_profile | profile_json = CompanyProfile, включая продукты/ФТС/платёжные доли |
| group_profile | profile_json = GroupProfile; только доступные участники GROUP_ID |
| factor / sector_sensitivity / product_factor_rule | Общая таксономия и проверенные правила; матрица только двух отраслей |
| app_user / auth_session / user_company_access | Учётки, хэши сессий, доступы company × ceo/cfo |
| source / news_raw | Конфигурация источника, исходный текст, URL, дата, статус и причина отказа |
| event / event_source / event_tag | Валидированная NewsExtraction и ссылки на явные дубли; не кластер событий |
| research_doc / research_page / research_chunk | PDF, страницы и блоки; PdfPageExtraction, ChartDraft и независимая сверка |
| feed_snapshot | Один последний порядок компании; items_json = FeedItemDto[]; role в ключе отсутствует |
| insight | Версия полной карточки; body_json = InsightDto только при ready |
| chat_message | Один вопрос и его ChatAnswerDto; история строго user × insight |
| feedback | Последняя оценка пользователя для company × event; hide влияет на его выдачу |
| background_job | Kind + типизированный payload из backend/AlfaNews.Contracts/Processing; одна последовательная очередь |
| agent_run / agent_step | Прогоны всех LLM-операций и понятный журнал шагов, не скрытые рассуждения |
| llm_usage / llm_cache | Фактический расход и кэш валидированных ответов |
| user_activity | Минимальный журнал действий: ID, серверное время, пользователь, компания, карточка, тип и ссылка evidence/action |

## Важные детали

- У payment нет FK на company: у части участников нет CLIENT-профиля. Такие платежи остаются в знаменателе внешнего оборота, но не добавляются в числитель отрасли. У компании cp может быть неизвестен при нулевом знаменателе; отдельное `Known=false` хранится в FeatureContribution.
- Одинаковые строки одного SYNTHETIC_U схлопываем; конфликтующие варианты исключаем из чистой company с отчётом. Нет company — нет пользовательского доступа и демо-профиля. Исходный файл не переписываем. Суммы повторяющейся пары платежей группируем один раз в рамках импорта; повторная загрузка того же пакета заменяет его агрегаты, не прибавляет их ещё раз.
- Поле REVENUE_COMPANY хранится в исходных единицах — рубли за 2025 год по текущему плану. 1000 — заглушка и становится null. Сумма известной выручки группы сопровождается RevenueKnownCount и неполнотой, не считается полностью известной выручкой.
- raw_data — объект с исходными именами 24 колонок и строковыми/null значениями. staging для COPY — временная техническая таблица; не отдельная модель продукта и не источник профилей из исключённых PROSPECT.
- event.extraction_json = NewsExtraction; опубликованную дату задаёт сборщик. event_source включает канонический news_raw и явные дубли; одинаковое значение content_sha256 не вызывает ещё один LLM-разбор.
- research_chunk.tables_json = TableDraft[]; chart_data = ReviewableChartDto[]. review_status блока не заменяет статус конкретного графика. OCR-модель выдаёт только ChartDraft, статус сверки выставляет сервер. Итог reviewed страницы возможен, только если все её блоки и графики просмотрены; итог документа агрегируется по страницам.
- Статусы OCR: ready — все страницы готовы, partial — часть готова и есть failed, failed — нет успешно распознанных страниц. Пока есть queued/running страницы, документ processing. Финализатор запускается после завершения попыток страниц, успешные блоки не теряются при ошибке другой страницы.
- search_text считает код с `to_tsvector('russian', ...)`; модель не пишет SQL. e5-base даёт 768 значений. Для недельного набора допустим точный vector search без отдельного HNSW; индекс добавляем только при измеренной необходимости.
- input_version — хэш версий данных, события, банковских фрагментов, правил, промпта, схемы и модели. У role отдельный ключ карточки. Кэш включает также параметры генерации и лимиты. Старый результат не показываем как новый после сверки OCR.
- SQL не выражает все содержательные ограничения JSONB: refs/числа/origin/сверку/доступ проверяет приложение. `body_json IS NOT NULL` само по себе не означает готовую карточку.
- Ни app_user.password_hash, ни auth_session.token_hash, ни server file_path, ни промпты/ключи не входят в API. PageImageUrl — разрешённый endpoint, не путь диска.
- `agent_run` создаём также для news_extract, pdf_ocr и chat; поэтому llm_usage.run_id всегда разрешается. card_id nullable, когда полной карточки ещё нет. Ошибочный запрос тоже имеет запись расхода/времени, даже если сервер не вернул usage.
- actual_cost_rub=null — провайдер не отдал usage/нет подтверждённого тарифа; это не нулевой расход. Резерв не освобождаем как будто запрос бесплатен: остаток учитываем консервативно до сверки. Политика одного Worker обходится без отдельной таблицы финансовых транзакций.
- При выдаче feed_snapshot API накладывает hide текущего пользователя и состояние нужной роли. Позиции rank сохраняются из общего порядка, не перенумеровываются по роли/скрытию. Дополнительные события вместо скрытого не генерируем.

- user_activity создаётся в первой миграции A02. Все текущие события относятся к карточке, поэтому company_id/insight_id обязательны и выводятся сервером из разрешённого insight. user_id и created_at также задаёт сервер. Текст вопроса, источника или произвольные metadata не принимаются. Для source_opened обязателен evidence_id из evidence карточки; для action_interacted — action_id из массива actions (ID утверждения действия). Для остальных типов оба поля null.
- ID браузерного события — UUID, новый для каждого фактического действия и сохранённый при повторе доставки. Точный повтор возвращает успех без второй строки; повтор ID с другим содержимым даёт 409. chat_question_accepted записывает только сервер после сохранения chat_message, используя ID сообщения для идемпотентности. D09/A13 вызывают RecordAcceptedChatAsync в той же транзакции, что сохранение принятого вопроса; повтор выполнения job не создаёт новое событие.
