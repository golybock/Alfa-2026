# A03: импорт компаний и платежей

При `docker compose up -d --build` сервис `migrate` сначала применяет миграции EF Core. Только после его успешного завершения запускается Worker. В Docker у Worker включён `Data__ImportOnStartup=true`: он импортирует `df_Uid_data_hack.csv` и `df_Uid_payment_hack.csv` из `/input`. Файл связей физлиц не читается. Исходники подключены только для чтения и не изменяются.

Импортер дополнительно проверяет отсутствие неприменённых миграций. Если схема не готова, загрузка запрещена; импортер сам миграции не применяет.

## Повторный запуск

Компании, платежи и запись `background_job` вида `ImportCsv` со статусом `done` сохраняются одной транзакцией. Payload соответствует `ImportCsvJob`, а `result_id` содержит два SHA-256 исходников. Worker проверяет завершённую версию `Data__DatasetVersion` под транзакционной advisory-блокировкой PostgreSQL. После успешного импорта той же версии с текущим фильтром автоматическая загрузка пропускается, CSV повторно не читаются. Импорты со старыми стадиями, включая `csv_imported` и `csv_imported_group_revenue_v1`, один раз обрабатываются заново; новая стадия — `csv_imported_known_payments_v1`. Наличие отдельных строк в таблицах без отметки завершения не считается полным импортом.

При ошибке CSV, отмене или невозможности записать отчёт транзакция откатывается; следующий запуск повторяет импорт. Одновременные запуски сериализуются одной блокировкой. Пустой допустимый пакет также имеет отметку завершения и не вызывает бесконечный повтор.

Ручная команда повторно обрабатывает пакет: суммы внутри файла агрегируются заново, сохранённые значения заменяются, а не прибавляются. Для уже импортированной версии другие хэши запрещены. Версия обозначает неизменный пакет; изменение версии не является очисткой или полной заменой всей базы. При применении фильтра из `company` удаляются ранее импортированные компании текущего пакета, попавшие в группы ниже порога; их пересчитываемые `company_profile` удаляются первыми. Из `payment` удаляются ранее сохранённые пары, у которых оба участника отсутствуют в итоговой `company`. Остальные связанные записи автоматически не удаляются: ограничения FK сохраняются, конфликт откатывает всю транзакцию. После ручного импорта и при запуске Worker выполняется [сборка профилей A04](a04-profiles.md).

## Очистка и отчёт

Ожидаются UTF-8, разделитель `;`, заголовки из `contracts/inputs.md`, десятичная точка. Поддерживаются BOM, кавычки, экранированные кавычки и переносы внутри поля. Неверный заголовок, повреждённый UTF-8 и нарушенное экранирование прерывают пакет. Неверное число колонок учитывается как отклонённая строка.

Компании проверяются в порядке: число колонок, отсутствующий ID, конфликтующие варианты ID по всему исходнику среди строк правильной ширины, тип не CLIENT, идентичный дубль, ошибки полей. Конфликт исключает все строки ID правильной ширины. ID и ОКВЭД остаются строками; ОКВЭД проверяется по структуре, флаги принимают пустое значение, `0.0` или `1.0`. Отрицательная, нечисловая или не помещающаяся в БД выручка исключает строку. Выручка `1000` превращается в `null` с `quality_flags=["revenue_placeholder"]`; все 24 исходных поля сохраняются в `raw_data`, включая исходную заглушку. Продукты, страны, группы и платёжные доли вычисляются в A04. `NEGATIVEMARK` не интерпретируется как риск.

После очистки суммируем известную выручку принятых CLIENT по непустому `GROUP_ID`. Компании групп с `SUM(revenue) < 15 000 000 000` исключаются как `group_revenue_below_threshold`; ровно 15 млрд допускается. Дубли, конфликтующие ID, не-CLIENT и ошибочные строки не участвуют в сумме. `NULL` не учитываются: если часть выручки неизвестна, сравнивается известная сумма; если неизвестна вся выручка группы, фильтр не срабатывает. Компании без группы также сохраняются. Платежи исключённых компаний остаются в базе, если второй участник есть в итоговой `company`.

Платежи проверяются в порядке: число колонок, пустой участник, самоперевод, сумма, количество. Суммы должны быть неотрицательными и представимыми без округления в `numeric(28,2)`, количество — неотрицательным целым в пределах `bigint`; форма `1.0` допустима. Повторы направленной пары суммируются по `PAY_AMT` и `PAY_CNT`. Если результат группы переполняет поле БД, все строки группы исключаются как `aggregate_overflow`. После агрегации исключаются пары, у которых ни плательщика, ни получателя нет в итоговой `company`; причина — `no_known_participant`. В отчёте считается число исходных строк этих пар. При проверке учитываются принятые компании пакета и уже существующие компании вне него, за исключением компаний, удаляемых по порогу группы. Если хотя бы один участник известен, платёж сохраняется в обоих направлениях, чтобы не изменить знаменатели платёжных долей.

Отчёт находится в `data/reports/import_report.json` на хосте, `/reports/import_report.json` в Worker. Это отдельный writable mount; исходный `/input` остаётся read-only. Отчёт содержит версию, SHA-256 обоих файлов и счётчики:

- `read`: число записей без заголовка;
- `accepted`: число сохранённых компаний или агрегированных платёжных пар;
- `accepted_source_rows`: число принятых исходных строк до объединения платежей;
- `merged_rows`: число объединённых платёжных строк сверх одной на пару;
- `excluded`: число строк по каждой причине исключения, ровно одна причина на строку;
- `quality`: дополнительные признаки, не являющиеся исключениями.

Для каждой таблицы `read = accepted_source_rows + sum(excluded)`, для платежей `accepted = accepted_source_rows - merged_rows`. Идентичные дубли компаний учитываются в `excluded.identical_duplicate`. `quality.pairs_with_missing_profile` — число принятых пар с одним участником без записи в итоговой `company`; второй участник известен, поэтому эти пары не исключены. Отчёт детерминирован: время запуска в него не входит. Файл заменяется атомарно перед commit; при ошибке commit он может описывать ещё не завершённую попытку. Источник подтверждения успешного импорта — транзакционная отметка в БД, а не наличие JSON.

Контроль текущего пакета: 85 525 строк компаний → 41 968 CLIENT после очистки → 10 226 компаний после фильтра групп; исключены 31 742 компании по порогу выручки, 12 строк конфликтующего ID и 43 545 остальных строк не CLIENT. Среди принятых — 80 заглушек выручки. Из исходных 1 380 585 строк платежей исключены 27 406 самопереводов и 1 113 766 строк без обоих участников в итоговой `company` (1 113 749 агрегированных пар). Осталось 239 413 платёжных пар: 19 107 с двумя известными участниками и 220 306 с одним. В сохранившейся выборке повторных пар нет; все 17 объединяемых строк относились к ничейным парам. Повторный импорт даёт тот же отчёт и суммы.

## Ручной запуск

Из корня репозитория после запуска Compose и успешного завершения `migrate`:

```powershell
docker compose run --rm worker import-csv /input/df_Uid_data_hack.csv /input/df_Uid_payment_hack.csv hackathon-2026-v1
```

На хосте задайте `ConnectionStrings__DefaultConnection` через окружение для доступного PostgreSQL с применёнными миграциями, затем:

```powershell
dotnet run --project backend/AlfaNews.Worker -- import-csv data/df_Uid_data_hack.csv data/df_Uid_payment_hack.csv hackathon-2026-v1
```

Локальная настройка `Data:ImportOnStartup` по умолчанию выключена; Compose включает её явно. Путь отчёта переопределяется `Data__ImportReportPath`, входной каталог автоматической загрузки — `Data__InputPath`. Неподдерживаемые аргументы ручной команды приводят к ошибке. Строку подключения не передавайте аргументом командной строки.

## Проверки

```powershell
dotnet build Alfa-2026.slnx
dotnet format Alfa-2026.slnx --verify-no-changes --no-restore
dotnet test backend/AlfaNews.Tests
docker compose logs migrate worker
docker compose restart worker
docker compose logs --since 1m worker
```

Интеграционные тесты требуют `ALFANEWS_TEST_CONNECTION`: отдельный PostgreSQL 17 с pgvector и правом создания тестовых БД. Без неё PostgreSQL-тесты явно пропускаются. Тестируются очистка, сохранение raw-полей, повторные суммы/отчёт, пропуск без чтения CSV, откат и повтор после ошибки, переполнение платёжных групп, запрет импорта до миграций, порог выручки групп, неизвестная выручка и однократное применение новых фильтров к старому импорту, удаление только ничейных платежей и сохранение обоих направлений для известных компаний.
