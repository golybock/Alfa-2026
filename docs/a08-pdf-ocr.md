# A08: PDF и постраничный OCR

Исполнение остаётся последовательным: один Worker, один обработчик за раз. OCR использует `LlmTask.PdfOcr` через `LlmGateway`, GLM low из текущей конфигурации A06. В разработке по умолчанию `MockLlm`; синтетическая фикстура проверяет конвейер, а не качество распознавания реального PDF.

## Приём файлов

`PdfScheduler` выполняет обход при запуске и каждые 15 минут. Проверяются PDF непосредственно в `Data:InputPath` и в `Storage:RootPath/inbox`. Индекс `Data:InputPath/bank_research/index.json` даёт известные метаданные по SHA-256. Неизвестные дата и источник остаются null, при отсутствии названия используется имя файла без расширения. Файлы младше пяти секунд пропускаются до следующего обхода; при ручном копировании рекомендуется временное расширение с переименованием в `.pdf` после окончания записи.

Одинаковый SHA-256 не запускает новый OCR, даже после завершения или ошибки. Изменение содержимого создаёт отдельный документ. Ошибки повторяются явно. Для одновременных регистраций одного хэша используется транзакционная advisory lock PostgreSQL; регистрация и постановка IndexPdf атомарны. Исходный файл сначала сохраняется отдельно от транзакции. Авария процесса до регистрации может оставить неиспользуемый файл в `files`, который сканер не обрабатывает.

`POST /api/admin/documents` принимает существующий multipart-контракт: `file` с MIME `application/pdf`, обязательный `title`, необязательные `published_on` и `source_url`. Требуются сессия оператора и разрешённый Origin. Проверяются сигнатура `%PDF-`, размер до 50 MiB и фактическое число страниц от 1 до 50 через pdfinfo. У файла случайное серверное имя. Source URL хранится как метаданные и не загружается. Ответ `202 DocumentAcceptedResponse` означает принятую работу. Новое задание создаётся сразу, без ожидания таймера.

Операторские `GET /api/admin/documents` и `GET /api/admin/documents/{id}` возвращают существующие DTO. `GET /api/jobs/{id}` проверяет владельца либо оператора. Изображение страницы выдаётся через `GET /api/research/{documentId}/pages/{pageNo}` после `RequireResearchPageAsync`. Ручной повтор — `POST /api/admin/jobs/{id}/retry`; HTTP принимает только failed. Для running сначала остановите Worker и используйте существующую CLI-команду `retry-job`.

## Обработка

`IndexPdf` создаёт страницы и OcrPdfPage для каждой страницы. PNG получается через pdftoppm с максимальной стороной 2200 пикселей, сохраняется в общем volume; при отсутствующем PNG обработчик страницы восстанавливает его из PDF. Poppler запускается без shell, с лимитом времени и завершением дочернего процесса при отмене.

`OcrPdfPage` передаёт шлюзу одно изображение, метаданные и разрешённые теги. Ключ операции основан на хэше документа и номере страницы, версия входа учитывает параметры рендера и словарь. Сохраняются исходный PdfPageExtraction, блоки, таблицы, графики, теги и russian FTS. Факторы берутся из таблицы factor; при отсутствии согласованных значений соответствующие списки тегов пустые. Векторы и поиск относятся к A09.

Шлюз проверяет схему, уникальность ID, форму таблиц, region и различие label/axis_estimate. Он же ограничивает повторы и общую починку. Handler не создаёт дополнительные HTTP-повторы. Сохранение результата страницы и постановка финализации выполняются транзакционно. Review страниц, блоков и графиков остаётся not_reviewed. Числа графиков не становятся разрешёнными для количественного использования от успешного OCR.

Ошибка страницы сохраняется как безопасный код в `research_page.last_error` и failed соответствующей job. Остальные страницы продолжают выполняться. После конечного состояния всех страниц `FinalizePdf` вычисляет ready/partial/failed. Ошибочная страница повторяется отдельно, успешные страницы не отправляются модели заново. Финализация ставит EmbedContent на новые версии блоков; обработчик embeddings реализуется в A09. До его подключения такие задания заканчиваются not_implemented по правилам A05, что не означает готовность векторного поиска.

## Перенос результатов

Даты публикации девяти документов заданы в `data/bank_research/index.json` (у Gold_digest_August26 известен только месяц, стоит 01.08.2026). 23.10 комплект распознан заново, уже с заполненным словарём факторов, поэтому у блоков есть теги `factors`. Миграция `RefreshBankResearchOcr` применяет обновлённый seed к базам, где старый уже был загружен: сопоставляет документы по SHA-256 и номеру страницы, обновляет дату, OCR страниц и блоки, не трогая вручную сверенные документы и страницы; векторы новых блоков пересчитывает планировщик.

Миграция `SeedBankResearchOcr` использует встроенный JSON с результатами реального прогона исходного комплекта. Она сохраняет документы, страницы, OCR, блоки и FTS. Существующий документ с таким же SHA-256 полностью сохраняется: миграция не смешивает другое извлечение и не перезаписывает ручную сверку. PNG и PDF в миграцию не включаются.

При первом обходе на другом устройстве Worker связывает локальные PDF с сохранёнными хэшами и восстанавливает копии исходников в storage. Отсутствующие PNG рендерятся локально при запросе страницы; LLM для этого не нужен. Повторная загрузка известного документа тоже восстанавливает отсутствующий исходник без OCR. Для переноса новых, не входящих в комплект документов нужна копия PostgreSQL и файлового volume. Down этой миграции не удаляет предметные данные.

Экспорт после завершения обработки исходного комплекта:

```powershell
python tools/export-research-seed.py --database alfanews_a08_validation
```

Экспортёр требует девять зарегистрированных документов и 64 конечных состояния страниц; queued/processing и несогласованные review-статусы отклоняются. После экспорта нужно пересобрать приложение, чтобы JSON вошёл в сборку.

## Локальная настройка

Относительные Storage:RootPath и Data:InputPath разрешаются от ближайшего родительского каталога с Alfa-2026.slnx; поэтому API и Worker из разных каталогов Rider используют общее хранилище. В опубликованном приложении без репозитория база относительных путей — рабочий каталог; укажите обоим процессам одинаковый абсолютный `Storage__RootPath`. `Data__InputPath` указывает на локальную папку PDF. Команды `pdfinfo` и `pdftoppm` должны быть в PATH; альтернативно задайте `Storage__PdfInfoPath` и `Storage__PdfToPpmPath`. В Docker оба приложения используют существующий volume `research-files`, Poppler установлен в обоих образах. nginx допускает 52 MiB тела multipart; Kestrel и FormOptions настроены на тот же размер, сам PDF ограничен 50 MiB.

```powershell
dotnet build Alfa-2026.slnx --no-restore -c Release -m:1 --disable-build-servers -p:UseSharedCompilation=false
dotnet test backend/AlfaNews.Tests --no-build --no-restore -c Release -m:1
```

Интеграционные тесты используют `ALFANEWS_TEST_CONNECTION`, создают временные БД и требуют Poppler в PATH. Основная БД не очищается. Проверяются гонка регистрации, повторный обход без вызовов LLM, частичный OCR, явный retry, лимит страниц, подпись файла и операторский HTTP-путь. Полная ручная сверка содержимого остаётся K03. Применение review (маршрут D10 и `ResearchReview`) описано в [A09](a11-agent.md#a09-индекс-и-поиск).
