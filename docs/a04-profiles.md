# A04: профили компаний, групп и платёжные доли

Вход — очищенные `company` и `payment` из A03. Сервис `ProfileBuilder` сохраняет `CompanyProfile` и `GroupProfile` в существующие JSONB-таблицы `company_profile` и `group_profile`. JSON сериализуется через `ContractJson` по действующим контрактам. Таблица `company_group` не требуется: состав группы определяется по `company.group_id`. Контракты, схема БД и зависимости не меняются.

## Запуск

В Docker включён `Data__BuildProfilesOnStartup=true`. Worker после успешных миграций вызывает импорт, затем отдельный `ProfileBuildService`. Проверка профилей выполняется и при пропуске уже завершённого CSV-импорта. Worker только оркестрирует вызовы сервисов.

```powershell
docker compose up -d --build worker
docker compose logs migrate worker
docker compose run --rm worker rebuild-profiles hackathon-2026-v1
```

Ручная команда `import-csv` после импорта также пересобирает профили. Отдельная команда `rebuild-profiles` не читает CSV повторно. На хосте, с подключением к PostgreSQL через переменную окружения:

```powershell
dotnet run --project backend/AlfaNews.Worker -- rebuild-profiles hackathon-2026-v1
```

Параметры: `Data:DatasetVersion`, `Data:BuildProfilesOnStartup` и `Data:ProfilesReportPath`. В локальном appsettings автоматическая сборка выключена; Compose включает её и задаёт путь `/reports/profile_candidates.json`, доступный на хосте как `data/reports/profile_candidates.json`.

## Признаки компании

Профили строятся для CLIENT указанной версии. ОКВЭД остаётся строкой, `okved2` — первые две цифры; регион, город, отрасль и очищенная выручка берутся из `company`. Из `raw_data` извлекаются возраст и жизненный цикл. Заглушка выручки из raw не восстанавливается.

Флаги `1.0` преобразуются в `rko`, `guarantee`, `loan`, `leasing`, `deposit`, `payroll`, `factoring`. `FTS_FLAG` и `NEGATIVEMARK` не являются продуктами или метками риска. Пропущенные значения не превращаются в утверждения об отсутствии продуктов вне этого банка.

Страны ФТС разделяются запятыми, нормализуются по регистру и пробелам, дедуплицируются и сортируются. Общий `CountryNames` использует русские наименования исходника; та же нормализация доступна последующему извлечению новостей. Неизвестные названия сохраняются и попадают в `unmapped_countries`, ISO-коды не генерируются. Новые алиасы требуют явного дополнения словаря и смены его версии. Страны сохраняются независимо от флага ФТС и не интерпретируются как направление торговли.

## Входящие и исходящие

SQL отдельно обрабатывает `beneficiary = company_id` и `payer = company_id`. Самопереводы и отрицательные суммы защитно исключаются; в очищенном импорте их уже нет. Отрасль контрагента берётся из `company` той же версии, а не из ещё не построенной `company_profile`.

- `total_external_amount` — весь неотрицательный внешний объём направления, включая неизвестных контрагентов.
- `known_sector_amount` — часть объёма с известным контрагентом и корректным `okved2`.
- `coverage = known_sector_amount / total_external_amount`.
- `sector_shares[okved2] = объём отрасли / total_external_amount`.

Контроль: внешний объём 100, отрасль X — 24, известные отрасли — 60: доля X равна `0.24`, coverage — `0.60`. Делить 24 на 60 нельзя. Доли представлены числами от 0 до 1, а не от 0 до 100. Входящие и исходящие не складываются.

При нулевом объёме суммы и coverage равны 0, `sector_shares={}`; это отсутствие наблюдений, а не доказательство отсутствия связей. Нулевые отраслевые объёмы не создают долей. Контрагенты без известной отрасли остаются в знаменателе. Если платежи выбранных компаний относятся к другой версии, сборка останавливается вместо скрытого уменьшения знаменателя.

## Группы и ограничения

Непустой `GROUP_ID` объединяет только доступных участников выбранной версии. `member_ids` отсортированы; `known_revenue_sum` — сумма известных значений, `revenue_known_count` — их число. Когда все значения неизвестны, сумма равна `null`, а не 0. Компания без группы не получает придуманную группу.

Полнота известной выручки доступных участников видна по `revenue_known_count / member_ids.Count`. Полнота фактического состава группы неизвестна: в базе только отфильтрованные CLIENT. Это ограничение явно указано в отчёте. Выручка относится к 2025 году; агрегаты платежей — к периоду 01.01–31.10.2026. Не выводим долг, валюты, условия договоров, инвестиционные планы или характер отношений компаний.

## Версии, повторный запуск и сохранение

`data_version` имеет вид `<dataset_version>:profiles:<sha256>`. Хэш зависит от версии алгоритма, словаря стран, очищенных компаний и всех платежей выбранных компаний. `imported_at` не участвует: повторный импорт того же пакета не меняет версию профилей. Изменение сумм, ОКВЭД, raw-признаков или состава группы меняет её.

Импорт и построение профилей используют одну advisory-блокировку PostgreSQL. Во время расчёта SHARE-блокировка `company` и `payment` фиксирует входные данные; агрегаты рассчитываются SQL. Результаты массово передаются через COPY во временные таблицы и сохраняются одной транзакцией. Запись `RebuildProfiles` со статусом `done` и `result_id=data_version` фиксируется вместе с ними. Общая очередь относится к A05 и здесь не реализуется.

Повторная ручная сборка не дублирует строки и не меняет `updated_at` одинакового JSON. Автоматическая сборка пропускается, если есть отметка успешного завершения этой версии, ожидаемые профили присутствуют, устаревших строк выбранного набора нет и отчёт соответствует версии. Удалённый профиль или отсутствующий/повреждённый JSON-отчёт восстанавливаются. Профили прежнего состава выбранного набора и пустые группы удаляются при пересборке.

При фильтрации компании в A03 её пересчитываемый `company_profile` удаляется до `company`. Прочие внешние ключи не обходятся. Ошибки, отмена и невозможность записать отчёт откатывают транзакцию. JSON-отчёт заменяется атомарно перед commit; при ошибке commit он может описывать незавершённую попытку. Источник завершённого результата — таблицы и отметка в БД.

## Отчёт для K04

`profile_candidates.json` содержит количества профилей, версии, три выбранные демо-компании из разных `okved2` и черновики каналов. Для каждого кандидата приложены действующий профиль, доступная группа и ограничения.

Для демо явно выбраны U_68157 (строительство, ОКВЭД 41.20.9) и U_71942 (обработка древесины, ОКВЭД 16.10); U_12959 (разработка ПО, ОКВЭД 62.01) — дополнительная компания. Порядок в отчёте соответствует этому списку. Каждый кандидат — отдельная компания; вложенная группа содержит её доступных участников и сумму известной выручки. Порог 15 млрд ₽ применяется к группе, поэтому собственная выручка компании может быть ниже. Автоматического подбора замен нет: отсутствующие в наборе компании не добавляются и не заменяются другими. Профили всех остальных компаний и групп продолжают строиться в БД.

У U_68157 есть признак кредита, у U_71942 и U_12959 — депозита без признака кредита. Продуктовые признаки не доказывают размер долга, условия договора или отсутствие кредитов вне банка. Платёжное покрытие включает внутригрупповые связи; его нельзя интерпретировать как покрытие внешних по отношению к группе контрагентов.

`sensitivity_draft` содержит вопросы для проверки спроса, финансовых продуктов и стран ФТС. `status=draft`, `weight=null`, `sign=null`: черновик не записывается в `sector_sensitivity` или `product_factor_rule` и не участвует в score до K04 и утверждения Артёма. Неизвестный код фактора остаётся `null`. Компании выбраны для демо, но актуальные новости и покрытие источниками ещё нужно проверить.
