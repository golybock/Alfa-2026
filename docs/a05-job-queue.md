# A05: последовательная очередь

Один Worker читает существующую таблицу `background_job`. Миграции, контракты и новые пакеты не добавлены. Изменения предназначены для локальной проверки перед ревью.

## Запуск

Строку подключения задайте через `ConnectionStrings__DefaultConnection` в окружении. Для штатного локального PostgreSQL адрес — `127.0.0.1:15432`, остальные параметры берутся из `.env`. Сам .NET-хост `.env` не загружает. Перед запуском примените существующие миграции.

```powershell
dotnet run --project backend/AlfaNews.Worker -- run-worker
```

Запуск без команды сохраняет прежнее поведение и также включает очередь. Стартовые импорт CSV и сборка профилей сохраняют свои настройки `Data:ImportOnStartup` / `Data:BuildProfilesOnStartup` и выполняются перед диспетчеризацией. Ручные `import-csv` / `rebuild-profiles` сохранены.

При старте единственного Worker все `running` автоматически возвращаются в `queued`, кроме записей с `last_error=llm_key_required`. Счётчик попыток сохраняется. Готовые и ошибочные задания автоматически не повторяются. Начатая работа может исполниться повторно, включая платный запрос: гарантии exactly-once нет. Ограничение одного запроса критика на версию карточки должно обеспечиваться предметным обработчиком через сохранённые результаты.

Ручной повтор:

```powershell
dotnet run --project backend/AlfaNews.Worker -- retry-job <uuid>
```

Команда возвращает `failed` или `running` в `queued`, очищает ошибку, старые даты исполнения и результат, сохраняет attempts. Для `running` сначала остановите Worker, чтобы не поставить повтор одновременно с живым обработчиком. Для заблокированных по ключу заданий сначала установите ключ в окружении сервера и перезапустите Worker, затем явно выполните `retry-job`. Несуществующие, `queued` и `done` задания команда отклоняет.

## Постановка и обработчики

`JobQueue.EnqueueAsync<T>` принимает готовый серверный контекст владельца/компании и существующий тип `*Job`. `FindActiveAsync<T>` ищет `queued/running` с теми же kind, JSONB-payload, владельцем и компанией. При последовательной повторной постановке возвращается существующая запись. Защиты от гонки нескольких параллельных производителей через уникальный индекс нет. Перед вызовом из HTTP требуется проверка доступа через `AccessService`; эти внутренние методы не заменяют авторизацию. `company_id` нельзя брать из ответа LLM.

Виды сохраняются как `ImportCsv`, `ParseNews` и т. д., в соответствии с уже существующим журналом импорта и профилей. Payload сериализуется настройками `ContractJson`. Приоритет: импорт 100, профили 90, сбор/разбор новостей 80, свежесть ленты 70, карточки/чат 60, финализация/индекс PDF 30, embedding 20, демо 10, OCR 0. Большее число выбирается первым, затем идут время создания и UUID. Работающий обработчик не прерывается новым заданием.

Обработчик реализует `IJobHandler`, регистрируется как scoped и возвращает `JobResult`. Подключены реальные `ImportCsvJobHandler` и `RebuildProfilesJobHandler`. Они используют существующие сервисы, а запись результата импорта/профилей обновляет исходное задание в транзакции данных. Прямые команды и стартовые сервисы продолжают создавать собственную запись результата, как раньше.

Все 13 контрактных видов известны диспетчеру. Для неподключённого обработчика и неизвестного kind сохраняется `failed/not_implemented`; успешная обработка не имитируется. Несовместимый JSON даёт `invalid_payload`. Ошибка обработчика даёт `failed/job_failed`, следующие задания продолжаются. `JobResult(ErrorCode: "llm_key_required")` позволяет предметному обработчику явно заблокировать работу до ручного повтора. Очередь не делает HTTP-повторы: их ограничения относятся к LlmGateway и предметным операциям.

Перед обработкой сохраняются `running`, stage, время старта и увеличенный attempts. Диспетчер использует отдельный DI scope для обработчика, чтобы не сохранять его незавершённые EF-изменения после ошибки. Остановка по CancellationToken оставляет `running` для восстановления при следующем старте. При ошибке связи с очередью Worker ждёт пять секунд и продолжает. При пустой очереди проверяет её раз в секунду.

`JobQueue.ToResponse` формирует существующий `JobResponse`: исключает payload, владельца, пути файлов, хэши пакетов и текст исключения. Публичные результаты разрешены только для типов `insight`, `chat_turn`, `document`, `feed`. Выдавать ответ можно только после `AccessService.RequireJobAsync`. HTTP-endpoints постановки и статуса относятся к D09 и здесь не добавляются. В журнале ошибок очереди сохраняются ID, kind и тип исключения, без текста входных данных или исключения.

## Расписание

Отдельный `JobScheduler` использует `PeriodicTimer` с интервалом 120 секунд. Первая постановка выполняется при запуске. Ставит общий `CollectNewsJob` со списком включённых источников и `RefreshFeedJob` только для CLIENT-компаний из настройки `Feed:CompanyIds` (ID через запятую). Пустой список отключает автоматический пересчёт ленты, сбор источников продолжает работать. Дубликаты и пробелы убираются, неизвестные ID и компании других типов пропускаются. Активный общий сбор и активный общий пересчёт конкретной компании не дублируются, даже если изменился AsOf. Планировщик может ставить задания во время долгого обработчика. До подключения предметных обработчиков они завершаются `not_implemented` и могут появляться снова на следующем такте.

## Проверки

```powershell
dotnet build Alfa-2026.slnx --no-restore -m:1
dotnet format Alfa-2026.slnx --no-restore --verify-no-changes
dotnet test backend/AlfaNews.Tests --no-restore -m:1
```

Для PostgreSQL-тестов задайте `ALFANEWS_TEST_CONNECTION` с правом создания временных БД. Fixture создаёт отдельную случайную БД, применяет миграции и удаляет её после проверки. Основная БД приложения не очищается. Без переменной интеграционные тесты явно пропускаются.

Покрыты последовательная обработка, приоритет свежих новостей перед OCR, порядок по времени, продолжение после ошибки и отсутствующего обработчика, типизированный payload, разделение владельцев/компаний, автоматическое восстановление `running`, сохранение attempts при повторе, блокировка по ключу, дедупликация расписания при изменении AsOf, безопасный JobResponse и реальные импорт/профили без дублирующих записей заданий.

Поддерживается ровно один исполняющий Worker. Lease, heartbeat, distributed locks, автоматическое восстановление работающего процесса и параллельный OCR в этой реализации отсутствуют.

## Тестовое сообщение каждые 10 секунд

Для проверки очереди включите внутреннее задание `ConsoleMessageJob`:

```powershell
$env:TestJob__Enabled = "true"
$env:TestJob__Text = "Проверка очереди: привет из Worker!"
dotnet run --project backend/AlfaNews.Worker -- run-worker
```

Строка подключения должна быть задана через `ConnectionStrings__DefaultConnection`. Через 10 секунд после запуска и далее раз в 10 секунд планировщик ставит задание, обработчик выводит текст в консоль через `ILogger` и завершает его как `done`. Приоритет -10: тестовое сообщение ждёт завершения основной работы. Одинаковые активные тестовые задания не накапливаются. Завершённые записи остаются в `background_job`. По умолчанию тест выключен (`TestJob:Enabled=false`). Для отключения задайте `TestJob__Enabled=false` и перезапустите Worker.

## Ограничение автоматического пересчёта ленты

В `.env` задайте ID компаний через запятую:

```dotenv
FEED_COMPANY_IDS=company_a,company_b
```

Compose передаёт значение в Worker как `Feed__CompanyIds`. Для локального запуска задавайте `Feed__CompanyIds` в окружении напрямую. После изменения настройки пересоздайте контейнер:

```powershell
docker compose up -d --no-deps worker
```

По умолчанию список пуст: автоматических `RefreshFeedJob` нет. Настройка ограничивает постановку по расписанию; она не отменяет ранее поставленные задания и не запрещает отдельное явно запрошенное задание для другой компании. Сбор и разбор новостей, OCR и индекс PDF не создают персональные карточки сами по себе в текущей реализации: их предметные обработчики пока не подключены. Будущую массовую генерацию нужно явно ограничивать в соответствующем обработчике; наличие PDF в индексе само по себе не должно запускать генерацию на весь CSV.
