# A05: очередь заданий с параллельными полосами

Один процесс Worker читает таблицу `background_job`. Задания разделены на полосы: внутри полосы они выполняются по приоритету, сами полосы работают параллельно и не ждут друг друга. Новые пакеты не добавлены.

## Запуск

Строку подключения задайте через `ConnectionStrings__DefaultConnection` в окружении. Для штатного локального PostgreSQL адрес — `127.0.0.1:15432`, остальные параметры берутся из `.env`. API, Worker и EF-команды автоматически загружают ближайший родительский `.env`; переменные процесса имеют приоритет. `POSTGRES_*` преобразуются в локальную строку подключения, если `ConnectionStrings__DefaultConnection` не задана. Перед запуском примените существующие миграции.

```powershell
dotnet run --project backend/AlfaNews.Worker -- run-worker
```

Запуск без команды сохраняет прежнее поведение и также включает очередь. Стартовые импорт CSV и сборка профилей сохраняют свои настройки `Data:ImportOnStartup` / `Data:BuildProfilesOnStartup` и выполняются перед диспетчеризацией. Ручные `import-csv` / `rebuild-profiles` сохранены.

При старте единственного Worker все `running` автоматически возвращаются в `queued`. Задание, заблокированное ключом модели, завершается как `failed/llm_key_required` и в восстановление не попадает: его повторяют вручную. Счётчик попыток сохраняется. Готовые и ошибочные задания автоматически не повторяются. Начатая работа может исполниться повторно, включая платный запрос: гарантии exactly-once нет. Ограничение одного запроса критика на версию карточки должно обеспечиваться предметным обработчиком через сохранённые результаты.

Ручной повтор:

```powershell
dotnet run --project backend/AlfaNews.Worker -- retry-job <uuid>
```

Команда возвращает `failed` или `running` в `queued`, очищает ошибку, старые даты исполнения и результат, сохраняет attempts. Для `running` сначала остановите Worker, чтобы не поставить повтор одновременно с живым обработчиком. Для заблокированных по ключу заданий сначала установите ключ в окружении сервера и перезапустите Worker, затем явно выполните `retry-job`. Несуществующие, `queued` и `done` задания команда отклоняет.

## Постановка и обработчики

`JobQueue.EnqueueAsync<T>` принимает готовый серверный контекст владельца/компании и существующий тип `*Job`. `FindActiveAsync<T>` ищет `queued/running` с теми же kind, JSONB-payload, владельцем и компанией. При последовательной повторной постановке возвращается существующая запись. Защиты от гонки нескольких параллельных производителей через уникальный индекс нет. Перед вызовом из HTTP требуется проверка доступа через `AccessService`; эти внутренние методы не заменяют авторизацию. `company_id` нельзя брать из ответа LLM.

Виды сохраняются как `ImportCsv`, `ParseNews` и т. д., в соответствии с уже существующим журналом импорта и профилей. Payload сериализуется настройками `ContractJson`. Приоритет: импорт 100, профили 90, разбор важных новостей 83, фильтр заголовков 82, сбор 80, разбор вторичных 79, свежесть ленты 70, карточки/чат 60, финализация/индекс PDF 30, embedding 20, демо 10, OCR 0. Большее число выбирается первым, затем идут время создания и UUID. Работающий обработчик не прерывается новым заданием.

Полосы задаёт `JobKinds`, число исполнителей каждой — `Worker`:

| Полоса | Виды заданий | Исполнителей |
| --- | --- | --- |
| data | ImportCsv, RebuildProfiles, RefreshFeed, ConsoleMessage | 1 |
| news | CollectNews, CollectManualNews, TriageNews, ParseNews | `QUEUE_NEWS_SLOTS`, по умолчанию 4 |
| documents | IndexPdf, OcrPdfPage, FinalizePdf, EmbedContent | `QUEUE_DOCUMENTS_SLOTS`, по умолчанию 3 |
| insights | GenerateInsight, PrecomputeDemo | `QUEUE_INSIGHTS_SLOTS`, по умолчанию 2 |
| chat | AnswerChat | `QUEUE_CHAT_SLOTS`, по умолчанию 2 |

Так ответ чата не ждёт генерацию карточки, а разбор новостей не ждёт OCR. Внутри полосы порядок прежний: приоритет, затем время создания и UUID. Задание захватывается условным `UPDATE ... WHERE status = 'queued'`, поэтому два исполнителя одной полосы не возьмут одну запись. Число исполнителей задаётся в `.env` (`Queue:*Slots`, 1–16; полоса data всегда одна: импорт, профили и пересчёт ленты зависят от порядка). Общее число одновременных HTTP-запросов к модели ограничивает `LLM_MAX_PARALLEL_REQUESTS` (`Llm:MaxParallelRequests`, 1–16, по умолчанию 8); лишние исполнители ждут свободный слот, резерв бюджета считается внутри одного процесса Worker. Дневной лимит расходов — `LLM_DAILY_LIMIT_RUB` (по умолчанию 500 ₽); задания сверх лимита завершаются `budget_exhausted` и повторяются вручную. Замер 23.10 на основной базе: при 4 исполнителях новостей — 45 событий за ~10 минут (раньше ~1 в минуту).

Обработчик может вернуть `JobResult(Defer: true)`: задание возвращается в `queued` со стадией `deferred`, попытка не засчитывается, `created_at` сдвигается на текущий момент, чтобы другие задания того же приоритета шли раньше. Так ждёт карточка второй роли: `GenerateInsight` откладывается, пока по тому же событию и версии выполняется карточка другой роли, захваченная раньше (при одновременном захвате — с меньшим ID), и затем берёт общий план из кэша шлюза. При параллельном разборе один и тот же текст из двух источников может пройти проверку точного дубля одновременно; второй упирается в уникальный `content_sha256` при сохранении и привязывается к уже сохранённому событию как `exact_content_duplicate`, без сбоя задания (запрос к модели в этом редком случае оплачивается дважды). Склейка по e5 эту гонку не ловит: в момент проверки ни одно из событий ещё не сохранено, а по калибровке она выключена.

Обработчик реализует `IJobHandler`, регистрируется как scoped и возвращает `JobResult`. Подключены реальные `ImportCsvJobHandler` и `RebuildProfilesJobHandler`. Они используют существующие сервисы, а запись результата импорта/профилей обновляет исходное задание в транзакции данных. Прямые команды и стартовые сервисы продолжают создавать собственную запись результата, как раньше.

Все 13 контрактных видов известны диспетчеру. Для неподключённого обработчика и неизвестного kind сохраняется `failed/not_implemented`; успешная обработка не имитируется. Несовместимый JSON даёт `invalid_payload`. Ошибка обработчика даёт `failed/job_failed`, следующие задания продолжаются. `JobResult(ErrorCode: "llm_key_required")` позволяет предметному обработчику явно заблокировать работу до ручного повтора. Очередь не делает HTTP-повторы: их ограничения относятся к LlmGateway и предметным операциям.

Перед обработкой сохраняются `running`, stage, время старта и увеличенный attempts. Диспетчер использует отдельный DI scope для обработчика, чтобы не сохранять его незавершённые EF-изменения после ошибки. Остановка по CancellationToken оставляет `running` для восстановления при следующем старте. При ошибке связи с очередью Worker ждёт пять секунд и продолжает. При пустой очереди проверяет её раз в секунду.

`JobQueue.ToResponse` формирует существующий `JobResponse`: исключает payload, владельца, пути файлов, хэши пакетов и текст исключения. Публичные результаты разрешены только для типов `insight`, `chat`, `document`, `feed`. Выдавать ответ можно только после `AccessService.RequireJobAsync`. HTTP-endpoints постановки и статуса относятся к D09 и здесь не добавляются. В журнале ошибок очереди сохраняются ID, kind и тип исключения, без текста входных данных или исключения.

## Расписание

`JobScheduler` проверяет сроки каждые 30 секунд, первая проверка — при запуске. `sources.json` задаёт общий поток с опросом раз в час, `sources-specialized.json` — приоритетный раз в 15 минут. На каждый источник ставится отдельный CollectNews; сначала наступившие сроки специализированных источников. Активно собираемые исключаются. Каталоги загружаются при старте, пометка is_specialized и интервалы сохраняются в source.

После сбора и по таймеру NewsProcessingSchedule ставит пакеты TriageNews до 50 заголовков и до 50 активных ParseNews: сначала важность 1, затем 2; внутри важности — свежие публикации первыми. Подробности, миграция и проверки — в [A07](a07-news-processing.md).

RefreshFeed ставится только по собственному таймеру для CLIENT-компаний из `Feed:CompanyIds`: компания получает новое задание, если за `Feed:RefreshIntervalSeconds` (по умолчанию 86400, сутки) для неё не создавалось системное RefreshFeed и нет активного. Разбор новостей RefreshFeed не ставит. Пустой список отключает периодический RefreshFeed; кнопка «Обновить» в API по-прежнему ставит задание явно.

Для фрагментов аналитики банка без вектора планировщик ставит EmbedContent пакетом до 500 записей, но не чаще раза в 10 минут и только если нет активных EmbedContent. Так недоступный TEI не порождает поток упавших заданий.

## Проверки

```powershell
dotnet build Alfa-2026.slnx --no-restore -m:1
dotnet format Alfa-2026.slnx --no-restore --verify-no-changes
dotnet test backend/AlfaNews.Tests --no-restore -m:1
```

Для PostgreSQL-тестов задайте `ALFANEWS_TEST_CONNECTION` с правом создания временных БД. Fixture создаёт отдельную случайную БД, применяет миграции и удаляет её после проверки. Основная БД приложения не очищается. Без переменной интеграционные тесты явно пропускаются.

Покрыты последовательная обработка, приоритет свежих новостей перед OCR, порядок по времени, продолжение после ошибки и отсутствующего обработчика, типизированный payload, разделение владельцев/компаний, автоматическое восстановление `running`, сохранение attempts при повторе, блокировка по ключу, дедупликация расписания при изменении AsOf, безопасный JobResponse и реальные импорт/профили без дублирующих записей заданий.

Поддерживается ровно один процесс Worker. Lease, heartbeat и distributed locks отсутствуют. Полоса documents работает в один поток: параллельный OCR страниц одного документа не включён, потому что финализация документа рассчитана на последовательное завершение страниц.

## Тестовое сообщение каждые 30 секунд

Для проверки очереди включите внутреннее задание `ConsoleMessageJob`:

```powershell
$env:TestJob__Enabled = "true"
$env:TestJob__Text = "Проверка очереди: привет из Worker!"
dotnet run --project backend/AlfaNews.Worker -- run-worker
```

Строка подключения должна быть задана через `ConnectionStrings__DefaultConnection`. Через 30 секунд после запуска и далее раз в 30 секунд планировщик ставит задание, обработчик выводит текст в консоль через `ILogger` и завершает его как `done`. Приоритет -10: тестовое сообщение ждёт завершения основной работы. Одинаковые активные тестовые задания не накапливаются. Завершённые записи остаются в `background_job`. По умолчанию тест выключен (`TestJob:Enabled=false`). Для отключения задайте `TestJob__Enabled=false` и перезапустите Worker.

## Ограничение автоматического пересчёта ленты

В `.env` задайте ID компаний через запятую:

```dotenv
FEED_COMPANY_IDS=company_a,company_b
```

Compose передаёт значение в Worker как `Feed__CompanyIds`. Для локального запуска задавайте `Feed__CompanyIds` в окружении напрямую. После изменения настройки пересоздайте контейнер:

```powershell
docker compose up -d --no-deps worker
```

По умолчанию список пуст: автоматических `RefreshFeedJob` нет. Настройка ограничивает постановку по расписанию; она не отменяет ранее поставленные задания и не запрещает отдельное явно запрошенное задание для другой компании. Частота задаётся `FEED_REFRESH_INTERVAL_SECONDS` (Compose) или `Feed__RefreshIntervalSeconds`. Сбор и разбор новостей, OCR и индекс PDF персональные карточки сами не создают. Карточки ставит только RefreshFeed — для до пяти отобранных событий компании и двух ролей ([A10](a10-ranking.md)).
