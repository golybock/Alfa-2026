# A10: score и недельная лента компании

Ранжирование выполняет код, без LLM. Каждое слагаемое становится причиной «почему показано» с доказательствами `E*`.

## Словари

`data/taxonomy.json` — единый каталог факторов, правил «продукт → фактор» и матрицы чувствительности отраслей. Worker синхронизирует его с таблицами `factor`, `product_factor_rule`, `sector_sensitivity` при каждом старте (`TaxonomyCatalogLoader`), как каталоги источников. Строки, которых нет в файле, удаляются. Файл проверяется: неизвестный фактор, вес вне [0,1] или знак не из `positive/negative/mixed` отменяют загрузку целиком.

Матрица (`taxonomy-v2`, `reviewed_by: draft-calibrated`) заполнена для демо-отраслей 41 (строительство), 16 (обработка древесины) и 46 (оптовая торговля). Каналы и знаки — от продакта (CSV 23.10, веса только по силе канала: 1 / 0,75 / 0,5 / 0,25); веса откалиброваны на 63 реальных событиях ([отчёт](calibration-thresholds.md)): «41 × стоимость кредита» и «46 × ключевая ставка» подняты до 0,75. Правило продукта «зарплатный проект → налоги» удалено: налоговый тег ставится почти любой новости и пропускал шум. Утверждение весов — за Артёмом. Для остальных отраслей строк нет, признак `factor` для них равен 0 и отмечен `known=false` — это не доказанное отсутствие связи.

Те же факторы и полный справочник ОКВЭД2 передаются в извлечение новостей, поэтому теги событий совпадают с кодами ранжирования.

## Формула

`FeedRanking` считает шесть признаков в [0,1]:

| Признак | Значение |
| --- | --- |
| okved | 1, если среди ОКВЭД2-тегов события есть отрасль компании |
| factor | максимальный вес матрицы для отрасли компании и факторов события |
| product | 1, если правило связывает фактор события с продуктом компании |
| country | 1, если страна события есть среди стран ФТС компании |
| cp | максимальная из входящей и исходящей долей внешних платежей с компаниями затронутых отраслей; направления не складываются |
| group | максимум матрицы или правила продукта у другой компании той же GROUP_ID; ID этой компании не раскрывается |

`base = .25 okved + .30 factor + .15 product + .10 country + .15 cp + .05 group` (`ranking-v3`: веса калибровки 23.10 и развод сюжетов; до калибровки — `.25 factor + .20 product`), `recency = 2^(-ageDays/7)`, `score = recency × source.reliability × base`. Роль и наличие позиции банка в формулу не входят. Допуск: хотя бы один признак больше нуля, `base ≥ 0.30` (было 0,20), `score ≥ 0.15`, публикация попадает в окно; смысл порога: сильный отраслевой фактор (вес 1) проходит сам, средний — вместе с продуктом, продукт без фактора отрасли не проходит. Окно — с 00:00 МСК шестого предыдущего дня до `as_of`. Сортировка — score, дата публикации, ID; не больше пяти событий; слабые события ленту не добивают. Один сюжет занимает одно место: событие пропускается, если по e5 оно одного сюжета с уже отобранным или уже пропущенным — косинус ≥ `Ranking:SameStoryMinSimilarity` (0,93) либо косинус ≥ `Ranking:SameStoryTaggedMinSimilarity` (0,86) при общем факторном теге и публикациях не дальше `Ranking:SameStoryWindowHours` (24 ч). Освободившееся место занимает следующее событие по score. События без вектора не склеиваются. Обоснование — [калибровка](calibration-thresholds.md#развод-одинаковых-сюжетов-в-ленте-ranking-v3).

Событие-комментарий (`commentary` из разбора: заявление, интервью или ожидание без нового решения, данных или правила) получает половину веса фактора отрасли (`Ranking:CommentaryFactorShare` = 0,5, `ranking-v4`): реплика о ставке после заседания идёт ниже самого решения ЦБ, но не исчезает из ленты. Причина показывает это в тексте.

Значимость строки (`relevance.significance`) считает код по base, модель её не пишет: ниже 0,40 — низкая, 0,40–0,50 — средняя, от 0,50 — высокая. На 63 событиях × 3 компании base прошедших в ленту — 0,35 (одна связь: фактор отрасли с весом 1 и группа), 0,39–0,46 (фактор и продукт), 0,63 (три связи); полосы PRD 0,35/0,50 сделали бы почти всё «средним». Значимость пересчитывается при чтении и для снимков и карточек, сохранённых до появления поля. У каждой причины есть `label` до 40 знаков из таксономии (отрасль, фактор, «Ваш продукт: кредит», страны, «Ваши покупатели/поставщики», «Компания вашей группы»); полный текст — в `text`.

Веса, пороги, `CpEnabled` и `PrecomputeInsights` задаются секцией `Ranking` (`RankingOptions`), сумма весов должна быть равна 1. В контракте признаки — `RankingFeatureCode`, поле `has_bank_view` из `RankingResult` удалено.

## RefreshFeed

`FeedRefreshService` загружает профиль, профили группы, словари и события окна, считает score и перезаписывает `feed_snapshot` компании: `FeedItemDto` с причинами, вкладами и реестром доказательств. Затем для каждого отобранного события и ролей CEO/CFO ставит `GenerateInsightJob`, если карточки этой версии ещё нет (в том числе упавшей: её повторяют вручную); задания ставятся от свежей публикации к старой, поэтому свежие карточки готовы первыми. Автоматическое задание, чьё событие к запуску выпало из ленты компании (его вытеснили более свежие или сильные события), завершается со стадией `skipped` без вызова модели (`Ranking:InsightsOnlyForFeed`, по умолчанию включено). Карточку, которую открыл пользователь, делаем всегда. Карточки появляются по событию, а не по таймеру: после разбора новости `EnqueueForEventAsync` считает формулу для компаний из `Feed:CompanyIds` и ставит RefreshFeed только тем, для кого событие прошло порог. Порог задаётся в `.env`: `RANKING_MIN_BASE` и `RANKING_MIN_SCORE` (Compose передаёт их в `Ranking__MinBase` и `Ranking__MinScore`). Суточный таймер `Feed:RefreshIntervalSeconds` только освежает снимок; существующие карточки повторно не генерируются.

## Строка ленты для интерфейса (ALF-59)

`FeedService` при чтении добавляет к строке: `insight_headline` и `direction` готовой карточки выбранной роли (направление — знак первого из рисков и возможностей среди последствий, без них `neutral`; модель ставит важное первым), `queued_at` активного задания карточки, `retry_available` у упавшей карточки, пока попыток меньше трёх (`InsightService.MaxRuns`: первая и два повтора по кнопке через тот же `POST .../insight`). Ответ ленты несёт `last_collected_at` (последний успешный сбор любого источника) и `collection_failed` (у всех включённых источников последняя проверка закончилась ошибкой; это не `refresh_status`, который про пересчёт ленты).

## Проверки

`FeedRankingTests` — пример 0,39 (фактор и кредит), полосы значимости, метки причин, половинный вес комментария, свежесть и пороги, окно МСК, cp без сложения направлений, группа без раскрытия ID, порядок и лимит пяти. `FeedRefreshDatabaseTests` — снимок, окно, постановка карточек для двух ролей без дублей, чтение через `FeedService`. `FeedRowDetailsTests` — заголовок и направление готовой карточки, признак сбора, повтор упавшей карточки и предел попыток, действие «связаться с менеджером», названия шагов агента.

Демо-снимок: у `feed_snapshot` ключ (`company_id`, `mode`), `mode` — `live` или `demo` (миграция `FeedSnapshotMode`). Команда `dotnet run --project backend/AlfaNews.Worker -- precompute-demo [as_of]` ставит `PrecomputeDemoJob` для компаний из `Feed:CompanyIds` на зафиксированную дату (по умолчанию — текущий момент); запущенный Worker считает для каждой компании снимок `demo` по окну этой даты и ставит карточки CEO/CFO отобранных событий независимо от `Ranking:PrecomputeInsights`. Живой снимок при этом не меняется. Какой снимок отдаёт `GET /feed`, задаёт настройка API `Feed:Mode` (`FEED_MODE` в `.env`, по умолчанию `live`); контракт API не меняется. `RefreshFeedJob` и кнопка обновления всегда пересчитывают живой снимок, поэтому в режиме demo лента на сайте от них не меняется. `InsightAgent` берёт дату и причины из того снимка, где есть событие (живой в приоритете). Тест: `FeedRefreshDatabaseTests`.
